1. modul • 45 perc

Ubuntu Server felmérése, APT és VirtualBox-hálózat

Elmélet: az Ubuntu LTS (Long Term Support) kiadások hosszú támogatási idejük miatt jó szerveralapot adnak. Az APT a repositorykból telepít, frissít és kezel függőségeket.

1. Rendszerazonosítás

cat /etc/os-release hostnamectl uname -r
Akkor jó: Ubuntu 26.04 LTS / Resolute környezetet látsz.

2. Hálózati interfészek

ip -br link ip -br address ip route

Gyakori VirtualBox nevek: enp0s3 és enp0s8, de mindig a saját géped kimenetét használd.

3. Internet és csomagfrissítés

ping -c 3 1.1.1.1 sudo apt update apt list --upgradable
Ha nincs internet: ellenőrizd VirtualBoxban az Adapter 1 = NAT és Cable Connected beállítást, majd az ip route kimenetet.
K01: Ubuntu verzió + hostname.
K02: két hálózati interfész.
K03: sikeres internet ping és apt update.
2. modul • 45 perc

Netplan: statikus belső IP, SSH és PuTTY

Elmélet: Ubuntu Serveren a tartós hálózati konfigurációt a Netplan YAML-fájlok írják le. A szerver belső címe állandó, így a DHCP/DNS/FTP/HTTP szolgáltatások mindig ugyanazon a címen érhetők el.

1. A belső interfész azonosítása

ip -br link ip -br address

A példában enp0s8 az UBUNTULAB interfész. Ha nálad más a neve, a következő YAML-fájlban azt használd.

2. A meglévő Netplan-fájlok megtekintése

ls -l /etc/netplan sudo cat /etc/netplan/*.yaml
Fontos: a NAT interfész DHCP-beállítását hagyd meg. A laborhoz külön fájlban csak a belső interfészt konfiguráljuk.

3. Statikus UBUNTULAB-konfiguráció

sudo nano /etc/netplan/99-ubuntulab.yaml
network: version: 2 ethernets: enp0s8: dhcp4: false addresses: - 192.168.60.1/24
sudo chmod 600 /etc/netplan/99-ubuntulab.yaml sudo netplan generate sudo netplan try

Ha a próba jó, fogadd el, majd:

sudo netplan apply ip -br address ip route
Akkor jó: a belső kártyán 192.168.60.1/24 van, a default route továbbra is a NAT interfészen megy.

4. OpenSSH

sudo apt install -y openssh-server sudo systemctl enable --now ssh sudo systemctl status ssh --no-pager ss -lnt | grep :22

5. Windows ideiglenes statikus cím

  • IP: 192.168.60.10
  • Mask: 255.255.255.0
  • Gateway: üres
  • DNS: egyelőre üres
ipconfig ping 192.168.60.1

6. PuTTY

  1. Host: 192.168.60.1
  2. Port: 22
  3. Connection: SSH
  4. Jelentkezz be student felhasználóval.
whoami hostname ip -br address
K04: Netplan + statikus 192.168.60.1 cím.
K05: Windows ping.
K06: PuTTY sikeres bejelentkezés.
K07: systemctl status ssh + 22-es port.

Felhasználók, csoportok és fájljogosultságok

Elmélet: a Linux hozzáférés alapja az owner/group/others jogosultságrendszer. A hálózati szolgáltatások mögött ugyanazok a fájlrendszer-jogok dolgoznak.

1. Felhasználók és projektcsoport

sudo groupadd projekt sudo adduser anna sudo adduser bela sudo adduser vendeg sudo usermod -aG projekt anna sudo usermod -aG projekt bela id anna id bela id vendeg

2. Labor könyvtárak

sudo mkdir -p /srv/ftp/{anna,bela,kozos,nyilvanos} sudo chown root:root /srv/ftp sudo chmod 755 /srv/ftp sudo chown anna:anna /srv/ftp/anna sudo chmod 700 /srv/ftp/anna sudo chown bela:bela /srv/ftp/bela sudo chmod 700 /srv/ftp/bela sudo chown root:projekt /srv/ftp/kozos sudo chmod 2770 /srv/ftp/kozos sudo chown root:root /srv/ftp/nyilvanos sudo chmod 755 /srv/ftp/nyilvanos echo "Ubuntu labor nyilvanos mappa" | sudo tee /srv/ftp/nyilvanos/OLVASS_EL.txt

3. Jogosultságok értelmezése

ls -ld /srv/ftp /srv/ftp/* stat -c '%A %a %U %G %n' /srv/ftp/* namei -l /srv/ftp/kozos

4. Pozitív és negatív teszt

sudo -u anna touch /srv/ftp/anna/anna.txt sudo -u anna touch /srv/ftp/kozos/anna-kozos.txt sudo -u bela touch /srv/ftp/kozos/bela-kozos.txt sudo -u vendeg touch /srv/ftp/kozos/vendeg.txt ls -l /srv/ftp/kozos

Kea DHCP4 – automatikus Windows címzés

Elmélet: a Kea a DHCPv4-kérésekre címet, DNS-szervert és domainnevet ad. A Windows kliens ezután már nem igényel kézi IP-beállítást.

1. Telepítés

sudo apt update sudo apt install -y kea-dhcp4-server dpkg -l | grep kea
Ubuntu-megjegyzés: a teljes kea meta-csomag több Kea komponenst is telepít. Ebben a laborban csak az IPv4 DHCP-szerverre van szükségünk, ezért a kea-dhcp4-server csomagot használjuk.

2. Konfiguráció

sudo cp /etc/kea/kea-dhcp4.conf /etc/kea/kea-dhcp4.conf.orig sudo nano /etc/kea/kea-dhcp4.conf
{ "Dhcp4": { "interfaces-config": { "interfaces": [ "enp0s8" ] }, "valid-lifetime": 3600, "renew-timer": 900, "rebind-timer": 1800, "option-data": [ { "name": "domain-name", "data": "lab.test" }, { "name": "domain-name-servers", "data": "192.168.60.1" } ], "subnet4": [ { "id": 1, "subnet": "192.168.60.0/24", "pools": [ { "pool": "192.168.60.100 - 192.168.60.150" } ] } ] } }

3. Syntax check és indítás

sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf sudo systemctl enable --now kea-dhcp4-server sudo systemctl status kea-dhcp4-server --no-pager sudo journalctl -u kea-dhcp4-server -n 30 --no-pager

4. Windows DHCP-re állítása

ipconfig /release ipconfig /renew ipconfig /all
Akkor jó: 192.168.60.100–150 közötti cím, DNS = 192.168.60.1, suffix = lab.test.
169.254.x.x? Ellenőrizd a két VM Internal Network nevét, a Kea interfésznevét és a szolgáltatás naplóját.

BIND9 DNS – saját belső névtér

Elmélet: a DNS teszi lehetővé, hogy IP-cím helyett neveket használjunk. A forward zóna A rekordokat, a reverse zóna PTR rekordot tárol.

1. Telepítés

sudo apt install -y bind9 bind9-utils dnsutils sudo systemctl status bind9 --no-pager

2. named.conf.options

sudo cp /etc/bind/named.conf.options /etc/bind/named.conf.options.orig sudo nano /etc/bind/named.conf.options
options { directory "/var/cache/bind"; listen-on { 127.0.0.1; 192.168.60.1; }; listen-on-v6 { none; }; allow-query { localhost; 192.168.60.0/24; }; recursion yes; forwarders { 1.1.1.1; 8.8.8.8; }; dnssec-validation auto; };

3. Zónák

sudo nano /etc/bind/named.conf.local
zone "lab.test" { type master; file "/etc/bind/db.lab.test"; }; zone "60.168.192.in-addr.arpa" { type master; file "/etc/bind/db.192.168.60"; };

4. Forward zóna

sudo nano /etc/bind/db.lab.test
$TTL 1H @ IN SOA server.lab.test. admin.lab.test. ( 2026112001 1H 15M 1W 1H ) IN NS server.lab.test. server IN A 192.168.60.1 www IN A 192.168.60.1 ftp IN A 192.168.60.1

5. Reverse zóna

sudo nano /etc/bind/db.192.168.60
$TTL 1H @ IN SOA server.lab.test. admin.lab.test. ( 2026112001 1H 15M 1W 1H ) IN NS server.lab.test. 1 IN PTR server.lab.test.

6. Ellenőrzés

sudo named-checkconf sudo named-checkzone lab.test /etc/bind/db.lab.test sudo named-checkzone 60.168.192.in-addr.arpa /etc/bind/db.192.168.60 sudo systemctl restart bind9 dig @192.168.60.1 www.lab.test +short dig @192.168.60.1 -x 192.168.60.1 +short

7. Windows teszt

ipconfig /flushdns nslookup server.lab.test nslookup www.lab.test nslookup ftp.lab.test ping server.lab.test

vsftpd – jogosultságok hálózaton keresztül

Elmélet: az FTP-t csak az izolált oktatási hálózaton használjuk. A cél annak megértése, hogy a Linux fájljogosultságok hálózati hozzáférésnél is érvényesek.

1. Telepítés

sudo apt install -y vsftpd sudo cp /etc/vsftpd.conf /etc/vsftpd.conf.orig sudo nano /etc/vsftpd.conf
listen=YES listen_ipv6=NO anonymous_enable=NO local_enable=YES write_enable=YES local_umask=002 dirmessage_enable=YES use_localtime=YES xferlog_enable=YES connect_from_port_20=YES chroot_local_user=YES local_root=/srv/ftp pasv_enable=YES pasv_min_port=30000 pasv_max_port=30100 pam_service_name=vsftpd
sudo systemctl enable --now vsftpd sudo systemctl restart vsftpd sudo systemctl status vsftpd --no-pager ss -lnt | grep :21

2. Windows teszt

ftp ftp.lab.test

Anna felhasználóval:

dir cd anna put anna-win.txt cd .. cd kozos put anna-win.txt cd .. cd bela quit
Akkor jó: anna ír az anna és kozos könyvtárba, de bela könyvtárába nem léphet.

Ismételd meg vendeg felhasználóval: a nyilvános állomány olvasható, a közös könyvtárba írás tiltott.

sudo find /srv/ftp -maxdepth 2 -type f -printf '%M %u %g %p\n' sudo journalctl -u vsftpd --since "15 minutes ago" --no-pager

nftables tűzfal és integrált hibakeresés

Elmélet: a daemon futása önmagában nem elég. A kliens → hálózat → tűzfal → szolgáltatás → fájljog teljes útvonalat kell ellenőrizni.

1. UFW ellenőrzése, nftables telepítés és mentés

sudo ufw status
Ebben a laborban közvetlen nftables szabályokat használunk. Ha az UFW aktív, a tanári környezetben kapcsold ki: sudo ufw disable, hogy ne két külön tűzfalszabály-rendszert hibakeress egyszerre.
sudo apt install -y nftables sudo cp /etc/nftables.conf /etc/nftables.conf.orig sudo nano /etc/nftables.conf

A példában a belső interfész enp0s8. Cseréld, ha nálad más.

#!/usr/sbin/nft -f flush ruleset table inet filter { chain input { type filter hook input priority 0; policy drop; iif "lo" accept ct state established,related accept ip protocol icmp accept iifname "enp0s8" tcp dport 22 accept iifname "enp0s8" udp dport 67 accept iifname "enp0s8" udp dport 53 accept iifname "enp0s8" tcp dport 53 accept iifname "enp0s8" tcp dport 21 accept iifname "enp0s8" tcp dport 30000-30100 accept iifname "enp0s8" tcp dport 80 accept } chain forward { type filter hook forward priority 0; policy drop; } chain output { type filter hook output priority 0; policy accept; } }
sudo nft -c -f /etc/nftables.conf sudo systemctl enable --now nftables sudo nft -f /etc/nftables.conf sudo nft -a list ruleset

2. Szándékos HTTP tűzfalteszt

Listázd handle azonosítókkal:

sudo nft -a list chain inet filter input

Keresd a tcp dport 80 accept szabály handle számát, majd ideiglenesen töröld:

sudo nft delete rule inet filter input handle HANDLE_SZAM

Windowsból frissítsd a weboldalt: most ne működjön. Ezután töltsd vissza a mentett konfigurációt:

sudo nft -f /etc/nftables.conf

3. Integrált állapotellenőrzés

systemctl --no-pager --type=service --state=running | grep -E 'ssh|kea|named|vsftpd|apache2|nftables' sudo ss -lntup | grep -E ':22|:21|:53|:67|:80' sudo nft list ruleset

4. Windows teljes teszt

ipconfig /all ping server.lab.test nslookup www.lab.test nslookup ftp.lab.test
  • PuTTY → server.lab.test
  • FTP → ftp.lab.test
  • Böngésző → http://www.lab.test
1. IP?→2. Ping?→3. DNS?→4. service?→5. port?→6. nftables?→7. log?
